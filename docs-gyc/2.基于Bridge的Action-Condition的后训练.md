## 一、背景与全链路图

### 1.1 Cosmos-Predict2.5官方Action Condition训练参考: Bridge

官方 Cosmos-Predict2.5 仓库里，`robot/action-cond` 这个发布模型是**基于 Bridge 数据集做 action-conditioned 后训练**得到的——单臂、7 维 action、256×320、13 帧。

我们的目标是在 **RoboTwin 双臂数据（14 维 action）** 上做同一件事。两件事共用同一套代码：同样的 `Dataset_3D`、同样的 DiT 主干、同样的 action 注入方式。唯一不同的是数据和超参。

**所以，在改 RoboTwin 之前，必须先把 Bridge 官方是怎么做的弄清楚**：数据长什么样、action 怎么算、模型怎么接进去、训练怎么配、推理怎么跑。这是本文的全部目的。

### 1.2 全链路一览

```
┌─────────────────────────┐
│ Bridge 数据集             │
│  annotation/*.json       │    ← 每 episode 一份标注 + 一段视频
│  videos/*.mp4            │
└─────────────┬───────────┘
              │
              ▼
┌─────────────────────────┐
│ Dataset_3D 预处理         │
│ · 读 state (7 维绝对位姿) │
│ · 算相邻帧相对变换 → action│
│ · ×20 scaler              │
│ · 采样 13 帧, resize 256×320│
└─────────────┬───────────┘
              │  data = { video:[C,13,256,320], action:[12,7], ... }
              ▼
┌─────────────────────────┐
│ DiT 2B 主干 (Cosmos v1 2B)│
│ · 视频 tokenizer 时间 4×压缩│
│ · action 两个 MLP 注入    │
│   — 加到 timestep emb     │
│   — 加到 adaln 调制       │
└─────────────┬───────────┘
              │
              ▼
    Rectified Flow 训练
    · ckpt 起点：T2V 后训练 iter_10000
    · batch=8, lr=32e-5, max_iter=150k
              │
              ▼
    DCP → model_ema_bf16.pt
              │
              ▼
    推理：1 帧条件 + 12 动作 → 生成 13 帧视频
    长序列 → chunk 自回归拼接
```

## 二、Bridge 数据集

### 2.1 数据来源

我们用的 Bridge 数据经过了两层传递：**原始数据（Berkeley）→ IRASim 打包 → Cosmos 下载**。

**原始数据集：BridgeData V2**（UC Berkeley RAIL 实验室开源）
- 机器人：WidowX 250（桌面单臂，6-DoF + 平行夹爪）
- 任务：桌面物体抓取 / 放置 / 推拉等基础操作
- 全量规模：约 60,000 条轨迹
- 官方主页：https://rail-berkeley.github.io/bridgedata/

Cosmos repo **不直接用 Berkeley 的原始数据**。我们吃的是字节 IRASim 团队在 BridgeData V2 基础上规范化打包后的版本（统一成 `annotation/*.json + videos/*.mp4`）：https://github.com/bytedance/IRASim

Cosmos 的 `Dataset_3D` 类就是从 IRASim 的 `dataset/dataset_3D.py` 抄过来改的，`cosmos_predict2/_src/predict2/action/datasets/dataset_local.py` 第 20–22 行有写明：

```python
"""
Adapted from:
https://github.com/bytedance/IRASim/blob/main/dataset/dataset_3D.py
"""
```

关于 train / val / test 的打包方式：IRASim 的 `bridge_train_data.tar.gz` **是一个 tar 包同时包含 train / val / test 三个子集**，解压后对应 `annotation/{train,val,test}/` 和 `videos/{train,val,test}/`——依据是 IRASim 官方的 [`dataset_structure.txt`](https://github.com/bytedance/IRASim/blob/main/dataset_structure.txt)。三者由同一次打包流程产出，格式（分辨率、帧率、字段结构）统一；Cosmos 侧也是用同一个 `Dataset_3D` 类处理三者，`train_annotation_path` / `val_annotation_path` / `test_annotation_path` 只是不同的目录指针。

### 2.2 下载与路径

repo 里只有一个地方给了下载命令——`docs/post-training_video2world_action.md` 第 8–14 行：

```bash
mkdir -p datasets && curl -L \
  https://lf-robot-opensource.bytetos.com/obj/lab-robot-public/opensource_IRASim_v1/bridge_train_data.tar.gz \
  | tar -xvz -C datasets/
cd datasets && mv opensource_robotdata/bridge ./
```

目标路径必须是 `datasets/bridge/`，这个路径被硬编码在 `cosmos_predict2/_src/predict2/action/configs/action_conditioned/data.py` 第 33 行：

```python
base_path = "datasets/bridge/"
```

> ⚠️ **train 集实际 episode 数待确认**。BridgeData V2 全量约 60,000 条，IRASim 的 `bridge_train_data.tar.gz` 是否做了筛选未验证。下载后 `ls datasets/bridge/annotation/train | wc -l` 即可得到准确值。

解压后：

这张表里每一项分别由"官方文档 / 论文 / 配置"和"本地实测"两类来源给出——分开列清楚，避免把 MP4 容器元数据当成真实采样率。

| MP4 容器分辨率 | 480 × 640（H × W，decord 形状顺序） | 本地 decord 实测 6/6 一致 |
| Episode 帧数 | 26 / 28 / 32 / 34 / 38 / 49（6 个 test 样本） | 本地 decord 实测；train 集未逐个统计，因任务长短不同而变化 |
| `state` / `action` 维度 | 7 / 7 | 样例 `0.json` 字段（详见 §2.5） |

**Cosmos 训练时实际喂进网络的是什么**

这是最容易混的一步，单独拎出来说。看 `cosmos_predict2/_src/predict2/action/datasets/dataset_local.py:238-244`：

```python
def _load_video(self, video_path, frame_ids):
    vr = VideoReader(video_path, ...)
    frame_data = vr.get_batch(frame_ids).asnumpy()
```

`decord.VideoReader` 按**帧序号**取帧，**根本不查 MP4 header 里那个 fps 字段**。所以 Cosmos 侧关心的只有两件事（见 `exp_2B_action_conditioned_rectify_flow.py:603` 及 `data.py:74-75`）：

- `num_action_per_chunk=12` → 每个训练样本取 **13 帧连续画面**（1 初始帧 + 12 动作帧）
- `fps_downsample_ratio=1` → 从起始帧开始**每帧都要**，不跳帧
- `video_size=[256, 320]` → 在 `Dataset_3D.preprocess` 里 resize 到 **256×320（H×W）**

**所以每个训练样本就是 IRASim 打包 MP4 里连续 13 帧，resize 后的画面**。MP4 header 上写 3 fps 还是 5 fps 对训练完全没影响。

**那"相邻两帧隔多少毫秒"到底是多少？**

- BridgeData V2 原始遥操控制频率是 **5 Hz**（官方页明确）。
- Cosmos-Predict2.5 论文 Sec 6.6 也确认训练数据是 **5 FPS**（_"...is recorded at 5 FPS"_）。
- IRASim 把图像序列重打成 MP4 时，header 写的是 **3.0 fps**（decord 实测 6/6 一致）。
- 结合以上两点，**真实帧间步长就是 1/5 = 200 ms**（5 Hz）。MP4 header 的 3 fps 只是 mux 时写入的标称值，不代表帧序列被降采样过。Cosmos 侧反正不读这个值，只按帧序号抽帧。

一条间接证据：Cosmos 仓库里写 RoboTwin 配置的作者明显是**按"Bridge = 3 fps"来对齐的**——见 `cosmos_predict2/_src/predict2/action/configs/action_conditioned/data.py:228`：

```python
fps_downsample_ratio=10,  # RoboTwin 30 FPS → sample every 10 frames (~3 FPS, matching Bridge)
```

所以实操层面，**Cosmos 团队把 Bridge 当 3 fps 处理**（跟 MP4 header 一致）。这也是我们在 RoboTwin 侧要做 30 Hz → 3 Hz 降采样的原因。

**其他关键点**

- 原始采集分辨率 640×480（W×H），Cosmos 训练时 resize 到 **256×320**（H×W）。
- 单 episode 约 **5.2~9.8 秒**（按 BridgeData V2 源 5 Hz × 26~49 帧换算）。**训练对此不敏感**，只要 action 序列和视频帧是 1:1 对齐就行。

**train 集与 test 集同格式**的依据：

1. **同一 tar、同一次打包**：IRASim [`dataset_structure.txt`](https://github.com/bytedance/IRASim/blob/main/dataset_structure.txt) 里 `bridge_train_data.tar.gz` 的 `annotation/{train,val,test}/` 和 `videos/{train,val,test}/` 并列存放，命名规则一致，由同一条打包流水线产出。
2. **IRASim yaml 不区分 split 的源尺寸处理**：[`frame_ada.yaml`](https://github.com/bytedance/IRASim/blob/main/configs/train/bridge/frame_ada.yaml) 只靠 `mode` 字段切换 train/val，`video_size` 对三者通用。
3. **同一 `Dataset_3D` 处理三者**：Cosmos 侧 train / val / test 走相同代码路径，仅 `start_frame_interval` 不同（train=1，val/test=16），action 计算、scaler、预处理完全一致。
4. **BridgeData V2 原始数据本就标准化**：固定机器人 + 固定相机 + 固定采集脚本，原始规格统一。

> ⚠️ 表里"6 个 test 样本"一行只能代表 test 子集。train 集理论上同格式（依据如上），但**未逐个 decord 验证**。若后续在 train 集上发现分辨率 / 字段不符，回来修这段。

### 2.5 Annotation 字段定义

`0.json` 的 key 列表：

```python
['task', 'texts', 'videos', 'action', 'state',
 'continuous_gripper_state', 'episode_id', 'latent_videos']
```

逐字段定义：

- **`texts`** — `list[str]`，长度 1。任务的自然语言描述。
  ```json
  ["move the spatula to the far left corner behind the pot"]
  ```

- **`videos`** — `list[dict]`，长度 1。视频相对路径。
  ```json
  [{"video_path": "videos/test/0/rgb.mp4"}]
  ```

- **`state`** — `float[N, 7]`，N = 视频帧数。每帧末端执行器绝对位姿：`[x, y, z, roll, pitch, yaw, _]`，前 3 维位置（米），中 3 维欧拉角（弧度），第 7 维训练不读。
  ```json
  [[0.29545, -0.00325, 0.13786, -3.11266, -0.13805, -0.03239, 1.0], ...]
  ```

- **`continuous_gripper_state`** — `float[N]`。每帧夹爪实际开合度，0 = 打开，1 = 闭合。
  ```json
  [0.00051, 0.00051, 0.0, 0.00051, ...]
  ```

- **`action`** — `float[N-1, 7]`。IRASim 预先算好的相邻帧动作增量。⚠️ **训练不读此字段**，真实 action 由代码从 `state` 重算，算法见第三章。
  ```json
  [[1.4e-06, -2.2e-04, -1.5e-07, 1.4e-03, 8.2e-06, 6.2e-04, 1.0], ...]
  ```

- **`episode_id`** — `str`。episode 编号，日志标识用。

- **`task`** — `str`。与 `texts` 重复，训练不读。

- **`latent_videos`** — 预编码 latent，仅在 `pre_encode=True` 模式下使用。Bridge 训练配置为 `pre_encode=False`，此字段被忽略。

### 2.6 Annotation 字段速查表

| 字段 | 形状 | 训练使用 | 说明 |
|---|---|---|---|
| `texts` | `list[str]`, len=1 | ✅ | 文本 condition |
| `videos` | `list[dict]`, len=1 | ✅ | 视频相对路径 |
| `state` | `[N, 7]` | ✅（仅 `[:, :6]`）| 绝对位姿，第 7 维丢弃 |
| `continuous_gripper_state` | `[N]` | ✅ | 夹爪连续值 |
| `action` | `[N-1, 7]` | ❌ | 自带增量，训练重算不用 |
| `episode_id` | `str` | ✅（仅标识） | 日志用 |
| `task` | `str` | ❌ | 与 `texts` 重复 |
| `latent_videos` | — | ❌ | 仅 `pre_encode=True` 使用 |

训练真正读入的字段只有 **`texts`、`videos`、`state`、`continuous_gripper_state`** 四个。

## 三、Action-Conditioned 的定义与实现

### 3.0 概述

#### 起点：基座模型没有 action

Cosmos-Predict2.5 的模型谱系里（见 [`0.环境与模型配置.md`](0.环境与模型配置.md)），最基础的两个变体是 `base/pre-trained` 和 `base/post-trained`，它们**只做通用视频生成**：输入文本（和可选的参考图像），输出视频。

**基座模型完全没有 action 输入**——它没见过"动作"这个概念，也不知道机器人该怎么动。直接拿基座去做机器人世界模型（"机器人执行这些动作会发生什么"）是不可能的。

`robot/action-cond/` 这个变体的区别就在这里：它是**在基座基础上额外增加一路动作条件信号**，再后训练得到的。这也是为什么叫 "Action-Conditioned **后训练**"——起点是已训好的基座，重点是**让模型学会根据给定的动作序列生成视频**。加完这一路条件后，模型的输入变成：

- **必选**：1 帧初始画面 + 12 帧动作序列（新加的 action condition）
- **可选**：文本描述（训练时 20% dropout，推理默认 `guidance=0` 即不启用）

输出是 13 帧视频（1 帧条件 + 12 帧新生成）。

#### 前后对比

| | 基座（`base/post-trained`） | Action-Conditioned（`robot/action-cond`） |
|---|---|---|
| 必选输入 | text | **1 帧初始画面 + 12 帧 action** |
| 可选输入 | 参考图像 | text（训练 20% dropout，推理默认关） |
| 输出 | 视频 | 13 帧视频（1 帧条件 + 12 帧生成） |
| 用途 | 通用文/图生视频 | 机器人世界模型 |
| 模型结构 | DiT | DiT + **action MLP 分支** |
| 训练阶段 | 预训练 → 基础后训练 | 基础后训练 → **action-conditioned 后训练** |

#### 三侧改动总览

要加上 action 这一路 condition，数据、模型、训练**三侧必须同步改**：

- **数据侧**（3.1）：dataloader 多吐一个 `action` 张量
- **模型侧**（3.2）：DiT 外挂一条 action MLP 分支，注入到每一层
- **训练侧**（3.3）：Rectified Flow loss 微调整个模型（主干不冻，action MLP 从头学）

下面三节分别展开。

### 3.1 数据侧 —— 让 dataloader 吐出 action 张量

- 文件：`cosmos_predict2/_src/predict2/action/datasets/dataset_local.py`
- 关键实现：
  - `_get_robot_states`（line 281–293）：从 JSON 的 `state` 字段取前 6 维位姿 + `continuous_gripper_state` 取夹爪
  - `_get_actions`（line 295–354）：按相邻帧算**局部坐标系下的相对变换**，得到 `[12, 7]` 的 action
    - 位移 `rel_xyz = prev_rotm.T @ (curr_xyz - prev_xyz)`（投影到前一帧的机器人坐标系）
    - 姿态 `rel_rpy = rotm2euler(prev_rotm.T @ curr_rotm)`（前一帧到当前帧的相对旋转）
    - 夹爪 `curr_gripper`（**当前帧的绝对开合度，不是差分！**）
    - ⚠️ **gripper 是 action 里唯一不走差分的维度**：位移、姿态都是"相对前一帧的变化量"，gripper 却是"当前帧的绝对值"。这是反直觉的点——RoboTwin 侧适配双臂 14 维时，如果按直觉全走差分，会导致夹爪开合信号跟训练分布完全对不上。见 `dataset_local.py:353` 单臂和 `:317` 双臂分支，两处对 gripper 的处理都是 `gripper_states[k]`，不是 `gripper_states[k] - gripper_states[k-1]`。
    - **为什么是相对变换而非绝对位姿**：相对变换在不同初始位置下分布更平稳，对主干学习更友好；绝对位姿会把"机器人在什么地方"跟"机器人怎么动"纠缠在一起
  - `c_act_scaler = [20, 20, 20, 20, 20, 20, 1]`（line 145）：位移/姿态 ×20 放大，夹爪 ×1
    - **×20 的经验来源**：Bridge 单步位移量级在厘米级（0.01 m 量级），×20 后进到 0.2 量级，跟网络里其它 embedding 的动态范围对齐，防止 action 信号被 timestep embedding 淹没。这个值沿袭自 IRASim，Cosmos 没改。
  - `__getitem__`（line 369）：`actions *= self.c_act_scaler` → `data["action"]`
- 注册为 Hydra 数据集：`cosmos_predict2/_src/predict2/action/configs/action_conditioned/data.py` line 41–94 定义了 `bridge_13frame_480_640_train/val_dataset`
- 单臂/双臂的分叉（line 138–146）：`action_dim=7` 走单臂相对变换；`action_dim=14` 走双臂分支（左右臂各算一套相对变换，scaler 也复制一份）

### 3.2 模型侧 —— 在 DiT 上接一个 action MLP 分支

- 文件：`cosmos_predict2/_src/predict2/action/networks/action_conditioned_minimal_v1_lvg_dit.py`
- 新增类 `ActionConditionedMinimalV1LVGDiT` 继承基座 `MiniTrainDIT`（line 47），**主干权重完全复用**，只在外层接入：
  - 新增两个 MLP（line 68–81）：
    - `action_embedder_B_D`：输入 `action_dim × 12 = 84` 维，输出 `model_channels`
    - `action_embedder_B_3D`：同输入，输出 `model_channels × 3`
  - forward 里 `action` 被 rearrange 打平成 `[B, 1, 84]` 过两个 MLP（line 111–113）
  - 注入点（line 142–143）：
    ```python
    t_embedding_B_T_D = t_embedding_B_T_D + action_emb_B_D     # 加到 timestep 嵌入
    adaln_lora_B_T_3D = adaln_lora_B_T_3D + action_emb_B_3D    # 加到 adaln 调制
    ```
  - **为什么同时注入两处**：
    - `timestep embedding` 是 DiT 的"全局条件"（去噪到哪一步），action 加到这里相当于让模型把"当前去噪阶段 + 要执行的动作"合成一个全局控制信号
    - `adaln_lora` 是 DiT **每一层 transformer block 都使用的调制信号**（scale / shift / gate），加到这里相当于让 action 调制整个 DiT 的每一层的归一化参数
    - 双路注入保证 action 信息在"全局 token"和"逐层调制"两个路径上都能传达，比只加一处收敛更稳
- 单臂/双臂的分叉：换双臂时 `action_dim` 从 7 变 14，两个 MLP 的输入维度变成 `14 × 12 = 168`——**MLP 的第一层权重 shape 变了，无法从单臂 ckpt 加载，必须随机初始化从头训**

### 3.3 训练侧 —— Rectified Flow loss 微调整个模型

- 文件：`cosmos_predict2/_src/predict2/action/models/action_conditioned_video2world_rectified_flow_model.py`
- 模型类 `ActionVideo2WorldModelRectifiedFlow` 继承 `Text2WorldModelRectifiedFlow`（line 65）
- **损失函数**：Rectified Flow 速度场损失 —— 模型预测从噪声到干净 latent 的速度 `v = x1 - x0`，loss 是预测速度与真实速度的 MSE（从父类 `Text2WorldModelRectifiedFlow` 继承，不是新写的）
- **训练哪些参数**：
  - 主干 DiT + 新增的 action MLP **一起参与梯度更新**（**不冻主干**）
  - `in_channels += 1`（line 50，给 condition mask 留出的输入通道）对应的新权重也从头学
- **权重起点（官方代码里的）**：
  - 所有 Bridge AC 配置的 `load_path` 都硬编码指向同一个 **NVIDIA 内部 S3** 路径：
    ```
    s3://bucket/cosmos_diffusion_v2/official_runs_text2world/
      Stage-c_pt_4-reason_embeddings-v1p1-Index-26-Size-2B-Res-720-Fps-16-
      Note-T2V_high_sigma_loss_reweighted/checkpoints/iter_000010000/model
    ```
    （见 `experiments/base/action.py:50` 和 `_src/.../exp_2B_action_conditioned_rectify_flow.py:570`）
  - 语义上是 Cosmos 内部某次 T2V 后训练的第 10000 步 ckpt。
  - **问题：这个 S3 bucket 不对公开用户开放**，按官方 post-training doc 的命令直接跑会加载失败；内部 ckpt 命名（`Stage-c_pt_4-...`）和 HuggingFace 上公开的 `base/pre-trained` / `base/post-trained`（见 [`0.环境与模型配置.md`](0.环境与模型配置.md)）也没有明文对应关系。
- **我们实际能用到的是训练成果，不是起点**：
  - HuggingFace `nvidia/Cosmos-Predict2.5-2B/robot/action-cond/38c6c645-..._ema_bf16.pt` 就是本章所讲训练流程跑完后的**最终 ckpt**（4.0 GB，BF16）。
  - 换句话说，虽然"用内部起点 + Bridge 数据做后训练"这一整段我们自己复现不了，但**它的产物 NVIDIA 已经直接发在 HF 上了**，我们直接下就能拿到。
  - RoboTwin 的迁移路线正是基于这一点：把这个已经训好的 `robot/action-cond` 当起点，在其之上做 14 维双臂适配（细节见 doc 5 / 6）。
- **加载策略**：`strict_resume=False`——主干权重原样复用；新增的两个 `action_embedder_*` MLP、以及 `in_channels+=1` 扩的那一路 patch embed 因为 ckpt 里没有对应权重，**随机初始化从头学**。

## 五、推理

### 5.1 单次推理：一次生成 13 帧

推理入口在 `cosmos_predict2/action_conditioned.py`（顶层薄封装）→ `examples/action_conditioned.py`（CLI 入口），跑的是 `Video2WorldInference.generate_vid2world`。

**输入输出**

| | 内容 | 形状 |
|---|---|---|
| 输入 | 1 帧初始画面 | `[1, 3, H=256, W=320]` |
| | 12 个 action 序列 | `[12, action_dim]`（单臂=7，双臂=14） |
| | 文本 prompt（可选） | 字符串，AC 默认空 |
| 输出 | 13 帧视频 | `[C, 13, 256, 320]` |

**核心步骤**（`action_conditioned.py:471–506`）

```python
img_tensor = to_tensor(img_array).unsqueeze(0)           # 初始帧
vid_input = torch.cat([img_tensor, zeros.repeat(12)], 0) # 填充 13 帧位
vid_input = (vid_input * 255.0).to(torch.uint8).unsqueeze(0).permute(0, 2, 1, 3, 4)  # [B, C, T, H, W]

video = video2world_cli.generate_vid2world(
    prompt="",                              # AC 默认关 text
    input_path=vid_input,                   # 初始帧 + 占位噪声
    action=torch.from_numpy(actions_chunk), # [12, 7] 或 [12, 14]
    guidance=0,                             # 推理关 CFG
    num_video_frames=13,
    num_latent_conditional_frames=1,
    num_steps=35,                           # 默认 35 步 RF 去噪
)
```

**关键推理参数**（`assets/action_conditioned/basic/inference_params.json`）

| 参数 | 默认值 | 含义 |
|---|---|---|
| `guidance` | **0** | AC 训练时 text 20% dropout，推理关 CFG |
| `num_steps` | 35 | RF 去噪步数，影响质量和速度 |
| `num_latent_conditional_frames` | 1 | 只用 1 个 latent 帧做条件 |
| `resolution` | `"256,320"` | 必须和训练一致 |
| `chunk_size` | 12 | 一次生成多少动作帧，跟 `num_action_per_chunk` 对齐 |
| `fps_downsample_ratio` | 1 | 推理时也不降采样 |
| `action_scaler` | 20.0 | 跟训练的 `c_act_scaler[:6]` 对齐 |

**推理 ≠ 训练的单位信息**

推理侧在 `cosmos_predict2/action_conditioned.py:62–103` 自己重写了一份 `_get_actions`（而不是复用 dataset 的），逻辑和训练完全一致：相邻帧相对变换 + `action_scaler=20` 缩放。这保证**推理时 action 分布和训练时一致**，不会因 scaling 不匹配翻车。

### 5.2 长序列生成：chunk 自回归拼接

单次推理只能出 13 帧（约 4 秒）。如果 episode 有 100 个 action，就要把它切成多个 chunk，**前一次生成的最后一帧作为下一次的初始帧**。

代码（`action_conditioned.py:471–515`）：

```python
for i in range(start_frame_idx, len(actions), chunk_size):
    actions_chunk = actions[i : i + chunk_size]
    # ... 推理出 13 帧 video ...
    next_img_array = video_clamped[-1]  # 取最后一帧
    img_array = next_img_array          # 下一次的初始帧
    chunk_video.append(video_clamped)
```

最后把所有 chunk 拼起来（第一个 chunk 保留 13 帧，后续 chunk 只保留 12 帧避免重复）：

```python
chunk_list = [chunk_video[0]] + [chunk_video[i][:chunk_size] for i in range(1, len(chunk_video))]
```

**这种拼接的问题**：误差累积。第二个 chunk 基于第一个 chunk 生成的（不完美的）最后一帧，第三个基于第二个……越往后画面越偏离真实轨迹。Bridge 训练的 episode 本来就短（~10 秒，1~3 个 chunk），误差累积不严重；RoboTwin 任务更长，需要在 doc 9（eval）里评估累积漂移。

## 六、蒸馏：35 步 → 4 步的加速方案

**动机**：RF 推理默认 **35 步**（`action_conditioned_config.py:86` 的 `num_steps: int = 35`），2B 模型单 chunk 在 H100 上约 10 秒。做 policy 评测要跑上百个 rollout，耗时难以接受。官方目标是把去噪步数从 **35 压到 4**——约 9× 加速。

### 6.1 蒸馏方案：DMD2

**DMD2**（Distribution Matching Distillation v2，原论文 [arXiv:2405.14867](https://arxiv.org/abs/2405.14867)）是把多步扩散/RF 教师模型蒸馏成少步学生模型的方法，关键特性：

- **Student 和 Teacher 网络结构相同**，区别只在推理步数（35 → 4）
- **同时蒸掉 CFG**（classifier-free guidance）：student 推理不需要 CFG，再省 2× 算力
- **训练时有一个辅助 critic 网络**（"fake score net"），和 student 交替更新
- Cosmos 侧用 **TrigFlow 参数化**（来自 sCM paper [arXiv:2410.11081](https://arxiv.org/abs/2410.11081)），统一了 DMD2 和 consistency distillation 两条蒸馏路线

原理细节见 `docs/distillation.md`——本章只关心怎么跑、用什么 ckpt。

### 6.2 AC 专属蒸馏实验

实验注册在 `cosmos_predict2/_src/interactive/configs/registry_experiment/experiments_dmd2_predict2p5.py:279`：

```
dmd2_trigflow_distill_cosmos_predict2_2B_action_conditioned_bridge_13frame_256x320
```

（`_no_s3` 后缀版本是同一实验但不依赖内部 S3，适合外部用户。）

**启动命令**（`docs/post-training_video2world_action.md:126–131`）：

```bash
torchrun --nproc_per_node=1 --master_port=12341 -m scripts.train \
  --config=cosmos_predict2/_src/interactive/configs/registry_predict2p5.py \
  -- experiment=dmd2_trigflow_distill_cosmos_predict2_2B_action_conditioned_bridge_13frame_256x320_no_s3
```

训练 ~4,000 步后，student 用 **4 步去噪** 已经能超过 teacher 用 4 步去噪的画质（官方图对比见 `docs/media/distillation_example.png`）。

### 6.3 蒸馏后推理

用蒸馏 ckpt 推理时，需要换三个参数（`docs/post-training_video2world_action.md:140–146`）：

```bash

  -o outputs/action_conditioned/basic \

```

三个关键改动：

- `--config-file`：从 action 配置换成 interactive（distill）配置
- `--experiment`：换成蒸馏实验名

### 6.4 对 RoboTwin 训练的参考

- HuggingFace **没有直接发布蒸馏后的 AC ckpt**——HF 上的 `robot/action-cond/..._ema_bf16.pt` 是 teacher（35 步），**想用 4 步加速版必须自己跑蒸馏训练**。
- 蒸馏的起点是已经训好的 AC teacher ckpt，所以：
  - **Bridge**：直接用 HF 上的 `robot/action-cond/` 当 teacher 蒸馏就行
  - **RoboTwin**：得先把 14 维 AC teacher 训出来（doc 5 / 6），再以它为起点蒸馏——链路比 Bridge 多一步
- 蒸馏不是本 Bridge 笔记的重点，只做指针：详细操作见 `docs/distillation.md` 和 `docs/post-training_video2world_action.md#4-distillation`。
