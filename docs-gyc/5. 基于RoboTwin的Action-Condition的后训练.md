## 一、背景

基于 **RoboTwin 双臂仿真数据**在 Cosmos-Predict2.5 上做 action-conditioned 后训练微调，得到一个能接受 **14 维双臂 action** 条件的视频生成模型。

与 doc 3（Bridge）的关系：Bridge 是官方给的单臂 7 维 reference 实现；本文做的是**同一套 pipeline 在双臂 14 维数据上的迁移**。Bridge 侧的数据格式、模型结构、训练机制、推理流程全部沿用，我们只负责 RoboTwin 侧的差异适配。

## 二、RoboTwin 数据集

> 本章讲的是**怎么把 RoboTwin 原始数据转成 Cosmos 能吃的格式**，核心思路：让转换后的格式跟 Bridge 的 annotation 完全同构（字段名、字段含义、目录结构都对齐），这样 Bridge 侧的 `Dataset_3D` 代码稍加改动就能直接复用。
>
> 操作层面的执行记录见 [`4.构造RoboTwin数据集.md`](4.构造RoboTwin数据集.md)；本章侧重"格式为什么这么设计、每一项跟 Bridge 怎么对应"。

### 2.1 原始数据来源与结构

RoboTwin 是 ByteDance 开源的机器人仿真数据集，我们用的是其中双臂操作的两个任务：

| 任务前缀 | 全名 | 含义 |
|---|---|---|
| `pcp` | `place_container_plate` | 把容器放到盘子上 |
| `pob` | `place_object_basket` | 把物体放到篮子里 |

**原始数据位置**：`/mnt/gyc/RoboTwin_ckp/data/{task_name}/region_all_clean/`

每个任务下有 4 个 region 子目录（`region_all_clean` / `region_all_random_background` / `region_back` / `region_front`），各 100 个 episode。**我们只用 `region_all_clean`**（干净背景），是最容易训的起点；后续扩大训练规模时可以把其他 region 也并进来。

**每个 region 目录的结构**：

```
region_all_clean/
├── data/
│   ├── episode0.hdf5    ← 末端位姿 + 夹爪动作数据
│   ├── episode1.hdf5
│   └── ...
├── video/
│   ├── episode0.mp4     ← 头部相机 RGB 视频（30 fps）
│   └── ...
├── instructions/
│   ├── episode0.json    ← 该 episode 的自然语言描述
│   └── ...
└── scene_info.json      ← 场景元信息（训练不用）
```

**`episodeN.hdf5` 里的关键字段**：

```
endpose/
  left_endpose    (N, 7)   [x, y, z, qw, qx, qy, qz]  ← 四元数!
  right_endpose   (N, 7)
  left_gripper    (N,)     0~1 开合度
  right_gripper   (N,)
joint_action/
  vector          (N, 14)  关节角度（训练不用）
observation/
  head_camera/rgb JPEG 序列  ← 视频文件已有，不读这个
```

**和 Bridge 的根本不同**：

| | Bridge | RoboTwin |
|---|---|---|
| 机器人 | WidowX 250（**单臂** 7 维） | 双臂 UR5 类（**双臂** 14 维） |
| 位姿表示 | 欧拉角 `[x,y,z,rpy]` | **四元数** `[x,y,z,qw,qx,qy,qz]` |
| 视频帧率 | 5 Hz（原始采集） | 30 fps（仿真渲染） |
| 格式封装 | IRASim 已打包成 `annotation/*.json + videos/*.mp4` | 原始 HDF5 + MP4，需要我们自己转 |

三处差异决定了 2.2 转换脚本要做的三件事：**四元数 → 欧拉角、双臂拼成 14 维、重新打包成 Bridge 格式的 JSON**。

### 2.2 数据转换：HDF5 → Cosmos JSON + MP4

转换脚本 `scripts/convert_robotwin_to_cosmos.py`（153 行，非常轻量）。

**总体流程**：

```
for task in [pcp, pob]:
    for episode in 0..99:
        1. 读 episode{N}.hdf5 的 endpose + gripper
        2. 每帧做：四元数 → 欧拉角，拼成 14 维 state
        3. 读 instructions/episode{N}.json 里的任务描述
        4. 软链接 video/episode{N}.mp4 → videos/{prefix}_{idx:04d}.mp4
        5. 写 annotation/{train|val}/{prefix}_{idx:04d}.json
最后 90% 做 train，10% 做 val（按排序顺序切）
```

**三个关键操作**：

**① 四元数 → 欧拉角**（`script:34–40`）

```python
def quat_to_euler(endpose):
    xyz  = endpose[:3]
    quat = endpose[3:]                             # [qw, qx, qy, qz]
    rotm = t3d.quaternions.quat2mat(quat)
    rpy  = t3d.euler.mat2euler(rotm, axes='sxyz')  # [roll, pitch, yaw]
    return np.concatenate([xyz, rpy])
```

**为什么必须转**：Bridge 的 `Dataset_3D._get_actions` 用 `euler2rotm(rpy)` 构造旋转矩阵来算相对变换（见 doc 3 §3.1）。如果直接把四元数塞进去，代码会把 `[qw, qx, qy, qz]` 误当作 `[r, p, y, _]`，产生完全错误的 action。

欧拉轴顺序选 `'sxyz'`（静态 XYZ）是跟 `transforms3d` 默认一致；Cosmos 侧的 `rotm2euler` / `euler2rotm` 也是按这个约定，确保可逆。

**② 14 维 state 拼接**（`script:55–64`）

```python
state[i] = [
    # 左臂 6 维（xyz + rpy）
    lx, ly, lz, lr, lp, lyw,
    # 右臂 6 维
    rx, ry, rz, rr, rp, ryw,
    # 两个夹爪
    left_gripper[i], right_gripper[i],
]
```

**布局顺序严格对齐 `dataset_local.py` 的双臂分支**（见 `_get_actions` 14D 分支，doc 3 §3.1 提过）：

```python
arm_states = states[:, :12]        # (T, 12) — 左 6 + 右 6
gripper_states = states[:, 12:14]  # (T, 2)  — [left_g, right_g]
```

两边对**顺序**和**哪些位是 rpy、哪些位是 gripper** 必须一致，否则 action 计算会错位。

**③ continuous_gripper_state**（`script:68–71`）

```python
continuous_gripper_state = (left_gripper + right_gripper) / 2.0
```

**这个字段训练侧双臂分支并不读**（`dataset_local.py:292` `if action_dim == 14:` 分支里夹爪来自 `states[:, 12:14]`，不是这个字段）。这里只是为了**跟 Bridge annotation 字段保持字段同构**——向后兼容，万一有代码路径还在用，不会因为缺字段报错。

存成双臂均值只是一个"有意义的兜底值"，真实训练数据来源是 14 维 state 的最后两列。

### 2.3 转换后的目录结构

```
/mnt/gyc_ckp/cosmos-predict2.5-robotwin/
├── annotation/
│   ├── train/                    180 个 JSON（pcp × 90 + pob × 90）
│   │   ├── pcp_0000.json
│   │   ├── pcp_0001.json
│   │   ├── ...
│   │   └── pob_0089.json
│   └── val/                      20 个 JSON（pcp × 10 + pob × 10）
│       ├── pcp_0090.json
│       ├── ...
│       └── pob_0099.json
└── videos/                       200 个软链接 .mp4
    ├── pcp_0000.mp4 → /mnt/gyc/RoboTwin_ckp/data/place_container_plate/region_all_clean/video/episode0.mp4
    ├── pob_0000.mp4 → /mnt/gyc/RoboTwin_ckp/data/place_object_basket/region_all_clean/video/episode0.mp4
    └── ...
```

**两个设计决策**：

- **软链接不拷贝**：MP4 文件较大（每个几十 MB），200 个拷贝会多占 GB 级空间，软链接零成本。代价是训练时必须保证 `/mnt/gyc/RoboTwin_ckp/` 可访问——换机器时要检查。
- **重命名 `episode{N}.mp4` → `{prefix}_{idx:04d}.mp4`**：不同任务都有 `episode0.mp4`，直接软链接到同一个 `episodes/` 会名字冲突。加任务前缀 + 补零编号既避免冲突，又方便按前缀过滤。

**目录结构与 Bridge 的对应**：

| RoboTwin 路径 | 对应 Bridge 路径 |
|---|---|
| `annotation/train/*.json` | `datasets/bridge/annotation/train/*.json` |
| `annotation/val/*.json` | `datasets/bridge/annotation/val/*.json` |
| `videos/{ep_id}.mp4` | `datasets/bridge/videos/train/{id}/rgb.mp4` |

注意 Bridge 侧 video 按 `train/val/test` 分子目录，我们这边不分——因为 JSON 里的 `videos[0].video_path` 是相对路径，直接指向根 `videos/` 就行。

### 2.4 Annotation 字段定义（14 维 state）

一个 `pcp_0000.json` 的实际内容：

```json
{
  "texts":    ["place the container on the plate"],
  "videos":   [{"video_path": "videos/pcp_0000.mp4"}],
  "state":    [
    [-0.298, -0.314, 0.942, 0.0, 0.0, 1.591,   0.306, -0.313, 0.941, 0.0, 0.0, 1.581,   1.0, 1.0],
    ...                            ← 154 帧
  ],
  "continuous_gripper_state": [1.0, 1.0, ...],
  "episode_id": "pcp_0000"
}
```

**字段与 Bridge 的对照**：

| 字段 | RoboTwin 含义 | Bridge 含义 | 训练是否读 |
|---|---|---|---|
| `texts` | 任务描述，从 `instructions/episode{N}.json` 的 `seen[0]` 取 | 同 | ✅ |
| `videos` | `[{"video_path": "videos/{ep_id}.mp4"}]` | 同（但路径含 split 子目录） | ✅ |
| `state` | **`[N, 14]`**：左臂 xyz+rpy(6) + 右臂 xyz+rpy(6) + 左爪 + 右爪 | `[N, 7]`：单臂 xyz+rpy(6) + 占位 | ✅（双臂分支读 `:12` 和 `12:14`） |
| `continuous_gripper_state` | `[N]` 双臂夹爪均值 | `[N]` 单臂夹爪 | ❌（双臂分支忽略） |
| `episode_id` | `{prefix}_{idx:04d}`，例如 `pcp_0037` | 数字字符串 | ✅（仅日志用） |

**Bridge 有但我们没写的字段**：

- `action`（IRASim 预算的相邻帧增量）：训练本来就不读（见 doc 3 §2.5），省掉
- `task`：与 `texts` 重复，省掉
- `latent_videos`：`pre_encode=True` 才用，我们 `pre_encode=False`，省掉

这些省略不会影响训练——Bridge 的 `Dataset_3D` 也不读它们。

### 2.5 转换脚本关键细节

**train/val 划分方式**（`script:127–135`）：

```python
all_episodes = [...]               # pcp × 100 + pob × 100，共 200，按 prefix 和 idx 排序
val_start = int(total * 0.9)       # = 180
for i, ep in enumerate(all_episodes):
    split = "train" if i < 180 else "val"
```

**后果**：排序后 pcp 全部在前 100，pob 在后 100。按 i<180 切：
- train = pcp_0000~0099 (100) + pob_0000~0079 (80) = **pcp 偏多**
- val = pob_0080~0099 (20) = **只有 pob，没有 pcp**

**这是个 bug**：val 集任务分布和 train 严重不均，val loss 无法反映 pcp 任务的真实表现。当前训练还能用（val 只用来监督训不过拟合），但**做 policy 评测时必须从 train 里单独留一批 pcp 做真 test**，不能只看 val。

**建议修法**：按 prefix 分别切 90/10，再 concat（代码改 5 行）——这个改了之后旧的 ckpt 还能继续用，只是重新跑一次转换脚本，annotation 重写即可（视频软链接不变）。

**几个没踩到的坑但要意识到**：

- **四元数格式**：RoboTwin 用 `[qw, qx, qy, qz]`（w 在前），`transforms3d.quaternions.quat2mat` 默认也是 w-first，所以可以直接传。若将来数据源变了换成 `[qx, qy, qz, qw]`（ROS 风格），要做换序。
- **欧拉角轴顺序**：`axes='sxyz'` 是静态 XYZ 顺序，跟 Cosmos 侧 `rotm2euler` 的默认一致。换约定会让 action 分布漂移，但训练不会报错——很隐蔽，要抓就得对着 action 直方图看。
- **帧数不固定**：不同 episode 帧数不同（154 是一个典型值，但不是所有都 154 帧）。`Dataset_3D` 的滑窗逻辑（`start_frame_interval`）会自动适配，不用我们额外处理。
- **视频不转码**：RoboTwin 原始 mp4 是 H.264 @ 30 fps，`decord` 直接能读，不用重新编码；只是训练时 `fps_downsample_ratio=10` 抽帧对齐 Bridge 的 3 fps（见第三章）。

## 三、与 Bridge 训练的对齐

> **这一章的核心问题：为什么 RoboTwin 要做各种对齐操作？**
>
> 我们的训练起点是 Bridge 上已训好的 `robot/action-cond` ckpt（详见 doc 3 §3.3）—— HuggingFace 下载的 `..._ema_bf16.pt` 里的主干 DiT 权重是在 Bridge 数据分布上学出来的：**256×320 分辨率、3 fps 左右的时序密度、action 数值分布在某个量级**。
>
> 如果 RoboTwin 侧喂进去的分布跟 Bridge 差太远，主干学到的先验用不上——最好的情况是收敛变慢，最坏的情况是产生完全离谱的输出、loss 炸掉。所以**每一个对齐决策都是为了"让主干以为自己还在处理 Bridge 数据"**，这样它的先验才能迁移，只有那些被我们刻意改动的地方（action MLP、文本分支）才需要重新学。
>
> 对齐得越彻底，需要训的参数就越少，训练效率和稳定性就越高。反过来，**不能对齐的项（比如 action_dim 7→14）就成了整个训练里最脆弱的环节**——3.4 会重点讲。

### 3.1 对齐项总览

| 维度 | Bridge 值 | RoboTwin 原始值 | 我们的对齐做法 | 代码/配置位置 |
|---|---|---|---|---|
| **视频分辨率（输入网络）** | 256 × 320（H × W） | 240 × 320（H × W） | `Dataset_3D` 里 resize 到 256×320 | `data.py:232` `video_size=[256, 320]` |
| **视频帧率** | ~3 fps（IRASim 打包标称，见 doc 3 §2.4） | 30 fps | `fps_downsample_ratio=10` → 每 10 帧抽 1 | `data.py:228` |
| **每样本帧数** | 13（1 初始 + 12 动作） | 不限 | `num_action_per_chunk=12`，滑窗取 13 帧 | `data.py:229` |
| **VAE 时间压缩** | 4× | 4× | 沿用（见 doc 3 §3 的 13 → 4 latent 说明） | `exp_..._rectify_flow.py:637` `state_t=1+12//4` |
| **Action 维度** | 7（单臂） | 14（双臂） | ⚠️ **无法对齐**，action MLP 从头训 | `data.py:235` `action_dim=14` |
| **Action 算法** | 相邻帧相对变换（位姿差分） | —— | 直接复用 Bridge 算法，双臂各算一套 | `dataset_local.py:295-318` 14D 分支 |
| **Action scaler** | `[20]×6 + [1]` | —— | `[20]×6 + [1] + [20]×6 + [1]`（左右臂复制一份） | `dataset_local.py:141-142` |
| **Gripper 语义** | 绝对值（非差分） | —— | 同 Bridge，从 state[:, 12:14] 直读 | `dataset_local.py:317` |
| **State 坐标系** | 机器人基座系 | 机器人基座系 | 默认一致，无需转换 | —— |
| **Text prompt** | 启用（20% dropout） | 可启用 | 目前**启用**，从 instructions 文件读 | `convert_robotwin_to_cosmos.py:117-123` |
| **相机数** | `cam_ids=[0]`（正视角） | 多相机可选 | 只用 head camera（对应 Bridge cam_0） | `data.py:230` |

**一句话总结**：**帧数、分辨率、chunk 大小、VAE、action 算法完全对齐；采样率通过下采样对齐；action 维度无法对齐（必须 7→14）**。下面几节逐项展开。

### 3.2 分辨率对齐

- **Bridge 目标**：256 × 320（H × W）
- **RoboTwin 原始**：240 × 320（decord 实测）
- **做法**：`Dataset_3D` 的 `preprocess` 里 `Resize_Preprocess([256, 320])` resize 到 256×320
- **对齐结果**：W 完美对齐（320→320）；H 从 240 拉伸到 256（**+6.67%**），有轻微纵横比畸变，**未 pixel-perfect 对齐**

配置位置：`data.py:232` `video_size=[256, 320]`。

### 3.3 帧率对齐（30 → 3 fps 降采样）

**Bridge 实际采样**：按代码注释，Cosmos 团队是**按 3 fps 处理 Bridge** 的（见 doc 3 §2.4 的考证）。

**RoboTwin 原始**：30 fps（仿真渲染）

**对齐方式**：`fps_downsample_ratio=10`，每 10 帧抽 1 帧，实际进网络的就是 3 fps。

配置位置（`data.py:228`）：

```python
fps_downsample_ratio=10,  # RoboTwin 30 FPS → sample every 10 frames (~3 FPS, matching Bridge)
```

**机制**（见 `dataset_local.py:229`）：

```python
curr_frame_i += self.fps_downsample_ratio  # 每次跳 10 帧
```

滑窗逻辑变成：
- 从 frame 0 开始，取 `[0, 10, 20, 30, ..., 120]` 共 13 帧作为一个样本
- 下个起点是 frame 1（`start_frame_interval=1`，滑窗步长 1），取 `[1, 11, 21, ..., 121]`
- 以此类推

**每 episode 产出多少个样本？**

以 `pcp_0000`（154 帧）为例：
- 单样本跨 120 帧 + 起点可取 0..33，共 **34 个样本/episode**
- 180 train episode × 34 ≈ **6,100 个训练样本**
- 一个 epoch ≈ 6100 / 8 (batch) / N_GPU 个 iteration

这个量级跟 Bridge 的 ~20,000 episode × 少量滑窗相比算小，所以训练需要多跑几个 epoch 或者 `max_iter` 设大一点。

**为什么是 3 fps 不是别的数？**

理论上任何能 divide 30 且让动作量级跟 Bridge 相近的值都行。但 Cosmos 代码注释（doc 3 §2.4 查到的那条）明确对齐到 3 fps，所以我们就按 3 fps 走，不做自己的探索。**对齐一个已验证的值，比自己找最优值更稳**。

**物理意义**

- 3 fps → 相邻帧间隔 333 ms
- 13 帧窗口覆盖 **12 × 333 ms ≈ 4 秒** 真实世界时间
- 4 秒对双臂操作任务刚好够完整看到一个"靠近 → 抓取"或"移动 → 放置"的子动作

这也是为什么不做 1 fps 或 5 fps 的原因：1 fps 窗口 12 秒太长，单 chunk 生成难度过大；5 fps 窗口 2.4 秒又不够一个完整子动作——3 fps 是甜点。

**Discussion：降采样是否必要？**

架构上没有硬约束要求降采样（主干不绑物理 fps、action MLP 反正从头训），不做降采样也能跑通。**我们目前暂时按 30 fps 原样采样训练**（即 `fps_downsample_ratio=1`，不降采样），后续会观察效果决定是否要切回 3 fps。

### 3.4 动作维度：7 维 → 14 维

**这是整个 RoboTwin 训练最脆弱的一环**。为什么脆弱？因为 action_dim 是**唯一必须从头学**的部分，Bridge 主干的预训练权重在这里完全用不上。

**维度的构成对比**：

| | Bridge 7 维 | RoboTwin 14 维 |
|---|---|---|
| 位移 | `Δx, Δy, Δz` | `Δlx, Δly, Δlz`（左）+ `Δrx, Δry, Δrz`（右） |
| 姿态 | `Δroll, Δpitch, Δyaw` | 左右各 3 维 |
| 夹爪 | `gripper` | `left_gripper, right_gripper` |
| 小计 | 3 + 3 + 1 = 7 | (3 + 3 + 1) × 2 = 14 |

**连锁影响**：

MLP 输入维度 = `action_dim × num_action_per_chunk`：

- Bridge：7 × 12 = **84**
- RoboTwin：14 × 12 = **168**

两个 action MLP（`action_embedder_B_D` 和 `action_embedder_B_3D`）的第一层权重 shape：

- Bridge：`[hidden_dim, 84]`
- RoboTwin：`[hidden_dim, 168]`

**Shape 不同 → 无法从 Bridge ckpt 加载 → 必须随机初始化从头训**。

**这为什么是"最脆弱"**？

- **Bridge 主干 DiT**：shape 一致，权重原样 load，初期 loss 就很低
- **RoboTwin action MLP**：shape 不同，随机初始化，**初期完全不知道 action 该怎么用**——相当于模型"看到 action 张量但不理解"，生成会严重依赖视觉输入、几乎忽略 action

**后果**：训练初期（几千到上万步），生成的视频基本是"初始帧的静态延续"，action 信号对生成结果的影响很弱。loss 会降，但降的是主干在复用预训练先验，不是在学 action。**必须训够足够步数**让 action MLP 真正对齐到主干，action 条件才会生效。

**怎么判断 action MLP 学到了**？看生成视频在不同 action 下是否产生不同的机械臂运动（同一初始帧，喂不同 action 序列，生成结果应该明显不同）。如果一直都是类似的"缓慢飘移"，说明 action 还没对齐进去。

**加载策略的代码位置**（`exp_2B_action_conditioned_rectify_flow.py:684-687`）：

```python
checkpoint=dict(
    load_path=".../robot/action-cond/38c6c645-..._ema_bf16.pt",
    load_training_state=False,
    strict_resume=False,  # action MLP input dim changes 7→14, must be non-strict
    ...
),
```

**`strict_resume=False` 必须加**：不加的话 PyTorch 严格检查 state_dict 的 shape 匹配，遇到 `action_embedder_*.fc1.weight` 时 shape 不匹配直接报错，训练起不来。

**加载时会看到的日志**（正常的 warning，不要慌）：

```
WARNING: size mismatch for action_embedder_B_D.fc1.weight:
  ckpt has torch.Size([..., 84]), model has torch.Size([..., 168]). SKIPPED.
WARNING: size mismatch for action_embedder_B_3D.fc1.weight:  ... SKIPPED.
WARNING: missing keys in model (initialized from scratch):
  action_embedder_B_D.fc1.weight, action_embedder_B_D.fc1.bias,
  action_embedder_B_3D.fc1.weight, action_embedder_B_3D.fc1.bias, ...
```

看到这些是**预期行为**，说明加载策略生效。如果完全没 warning 反而要怀疑是不是加载路径错了或者配置没改到位。

### 3.5 其他对齐点

- **Gripper 非差分**：action 里的 gripper 维是**当前帧绝对开合度**，不是差分。RoboTwin 双臂分支 `dataset_local.py:316-317` 严格沿用了这个约定，别改成差分。
- **Text prompt**：启用，从 `instructions/episode{N}.json` 的 `seen[0]` 读。训练 20% dropout、推理 `guidance=0`，行为和 Bridge AC 一致。粒度比 Bridge 粗（同类任务可能共享 prompt），短期不是瓶颈。
- **State 坐标系**：都是机器人基座系下的末端位姿（xyz + 欧拉角），单位米 + 弧度。相对变换只看相邻帧差，绝对原点不同无影响——**天然对齐，不用处理**。
- **相机视角**：只用头部单视角 (`cam_ids=[0]`)，跟 Bridge 一致。RoboTwin 原始还有侧视角/腕部相机，目前不训多视角。

### 3.6 权重起点对齐

**核心问题**：RoboTwin 训练从哪个 ckpt 出发？

**官方 Bridge 的起点（我们用不了）**

Bridge 官方配置的 `load_path` 指向 NVIDIA 内部 S3（详见 doc 3 §3.3）：

```
s3://bucket/cosmos_diffusion_v2/official_runs_text2world/
  Stage-c_pt_4-reason_embeddings-v1p1-Index-26-Size-2B-Res-720-Fps-16-
  Note-T2V_high_sigma_loss_reweighted/checkpoints/iter_000010000/
```

语义上是 Cosmos 内部某次 T2V rectified-flow 后训练的第 10,000 步中间 ckpt。这个 bucket **不对公开用户开放**，按官方命令直接跑会失败。而且这个内部 ckpt 跟 HuggingFace 上发布的 `base/pre-trained` / `base/post-trained` 也**没有明确对应关系**——不能简单替换。

**我们的实际起点：Bridge 训练完的成品 ckpt**

HuggingFace 的 `nvidia/Cosmos-Predict2.5-2B/robot/action-cond/38c6c645-..._ema_bf16.pt`（4.0 GB，BF16）**就是 Bridge AC 训练跑完 150k 步后的最终产物**——也就是整个 doc 3 第三/四章描述的流程的终点。NVIDIA 把这个成品发出来给大家用，我们直接下载。

**这么做的含义**：

- Bridge 的路线：内部 T2V ckpt（**起点**，拿不到） → Bridge 数据后训练 → `robot/action-cond/..._ema_bf16.pt`（终点）
- 我们的路线：`robot/action-cond/..._ema_bf16.pt`（当作**起点**） → RoboTwin 数据后训练 → 我们自己的 14D ckpt（终点）

换句话说：**Bridge 的训练终点正好是我们的训练起点**。这是整条迁移路线能成立的根本前提——如果 NVIDIA 没把 Bridge AC 成品发出来，我们就得先自己跑一遍 Bridge 训练（而起点 ckpt 又拿不到），整条路就断了。

**配置位置**（`exp_2B_action_conditioned_rectify_flow.py:684`）：

```python
checkpoint=dict(
    load_path="/mnt/gyc_ckp/models/Cosmos-Predict2.5-2B/robot/action-cond/38c6c645-7d41-4560-8eeb-6f4ddc0e6574_ema_bf16.pt",
    load_training_state=False,  # 不恢复优化器状态，从 iter=0 开始数
    strict_resume=False,        # action MLP shape 不匹配，必须非严格加载（见 3.4）
    save_to_object_store=dict(enabled=False),
    load_from_object_store=dict(enabled=False),
),
```

**三个配置项的意义**：

- `load_path`：指向本地下载好的 HF ckpt（不是 S3 路径，不依赖内网）
- `load_training_state=False`：只加载模型权重，不加载优化器状态（lr scheduler、momentum 等），相当于**从 iter=0 重新开始训**但站在一个很强的起点上
- `strict_resume=False`：允许模型的 state_dict 里有 ckpt 里没有的 key（即新建的 14D action MLP），以及忽略 shape 不匹配的 key——这是 3.4 讲过的必要条件

**跟 Bridge AC 训练的差别**：

| | Bridge AC 训练 | 我们 RoboTwin 训练 |
|---|---|---|
| 起点 | 内部 T2V ckpt（通用视频生成先验） | Bridge AC ckpt（**已经学过 action 条件生成**） |
| 起点 "强度" | 中 | **强**（主干 + text encoder + VAE + action 机制全就位） |
| 需要学什么 | action MLP + `in_channels+=1` + 主干 finetune | 14D action MLP 重学 + 主干轻度 finetune |
| 理论上需要的 iter 数 | 多（150k） | **应该更少**（起点更强） |

所以 RoboTwin 训练的 `max_iter` 不需要跟 Bridge 的 150k 等齐——起点强意味着收敛应该更快。具体多少合适见 3.8。

### 3.7 帧数、动作、VAE latent 结构的对齐

一条链路把 **13 帧画面 / 12 个 action / 4 个 latent 帧 / VAE 压缩比** 全串起来——这几个值是互相咬合的，改一个就得全改。RoboTwin 沿用 Bridge 的所有选择，**这几个数对齐是自动的**（只要不动 `num_action_per_chunk`）。

**数据流的完整 shape 链**（以 batch_size=1 为例）：

```
Dataset 采样：
  视频 13 帧 × 256×320 × 3 通道  → video: [C=3, T=13, H=256, W=320]
  action 12 个 × 14 维           → action: [T=12, D=14]
         │
         ▼  Wan VAE 编码
┌────────────────────────────────────────┐
│ 空间压缩 8×：256/8=32, 320/8=40         │
│ 时间压缩 4×（causal）：(13-1)/4+1=4     │
│ 通道膨胀：3 → 16                        │
└────────────────────────────────────────┘
         │
         ▼
  latent: [C=16, T=4, H=32, W=40]
         │
         ▼  +condition_mask 扩一通道
  latent_with_mask: [C=17, T=4, H=32, W=40]
         │
         ▼  DiT 主干（action 通过两个 MLP 注入 timestep/adaln）
         │    · action [12, 14] → flatten → [1, 168] → MLP → [model_channels]
         │    · 加到 timestep embedding 和 adaln 调制
         ▼
  predicted_velocity: [C=16, T=4, H=32, W=40]
         │
         ▼  rectified flow 去噪迭代（训练算 MSE loss，推理 35 步）
  clean_latent: [C=16, T=4, H=32, W=40]
         │
         ▼  VAE 解码
  video: [C=3, T=13, H=256, W=320]
```

**每一个数字的决定因素**：

| 数字 | 从哪来 | 能改吗 |
|---|---|---|
| **13 帧画面** | 由 VAE 时间压缩比 4 决定，`T_pixel = (T_latent-1)×4+1`，选 `T_latent=4` → `T_pixel=13` | 理论可改（如 5/9/17 帧），但主干权重绑死在 13 帧训练，实际不能动 |
| **12 个 action** | `num_action_per_chunk=12 = T_pixel - 1`（相邻帧之间有 12 个间隔，每个间隔 1 个 action） | 跟 13 绑死，只要 T_pixel=13 就必然是 12 |
| **4 个 latent 帧** | Wan VAE 时间压缩 4×（见 `wan2pt1.py:882` `temporal_compression_factor=4`） | 不能动，VAE 结构决定 |
| **256×320 空间** | Bridge 训练目标；VAE 空间压缩 8× 后 = 32×40 latent 像素 | 理论可改（如 512×640），但主干权重绑死，改了就得重训 |
| **14 维 action** | 双臂 (6+1)×2 = 14 | 跟机器人形态绑死 |
| **168 MLP 输入** | `action_dim × num_action_per_chunk = 14 × 12` | 自动推出，不用手配 |
| **16 通道 latent** | VAE 输出通道；加 1 个 condition mask → 17 入网 | VAE 结构决定 |

**关键含义**：

- **对 RoboTwin 来说，从 13 帧到 4 latent 帧的整条链都不用改**——跟 Bridge 完全一致，代码原生跑通
- **唯一变的是 action 那一支**：14 × 12 = 168 的 MLP 输入导致 `action_embedder_*` 的第一层权重 shape 不同，只能从头训（3.4 讲过）
- **所以 "13 帧 / 12 action / 4 latent" 这三个数在 RoboTwin 侧是"零成本对齐"**——我们什么都不用做，只要数据 loader 吐出的 shape 对，代码全自动

这也解释了为什么不尝试别的帧数（比如 17 或 25）来喂更多信息：**主干的时间位置编码、VAE 的时间压缩、attention 的 temporal token 数全在 13→4 这个 shape 上训出来的**，改任何一个都要重训整个主干，得不偿失。

### 3.8 数据量与训练预算的对齐

**核心问题**：RoboTwin 数据量比 Bridge 少两个数量级，应该训多少步？多少 epoch？

**规模对比**

| 项 | Bridge | RoboTwin |
|---|---|---|
| Episode 数 | ~20,000（doc 3 §2.4 论文数据） | **180**（train），20（val） |
| 单 episode 帧数（原始） | 26~49 | ~150（不定） |
| 降采样比 `fps_downsample_ratio` | 1（不降） | **10** |
| 单 episode 有效帧数 | 26~49 | ~15 |
| 每 episode 能产出 13 帧样本数（滑窗步长 1） | 14~37 | ~3（帧数被压缩掉 90%） |
| **单 epoch 总样本数** | ~500,000（估算，20k × 25） | **~540**（估算，180 × 3） |

注意：RoboTwin 降采样后每 episode 只剩 ~15 帧，13 帧窗口能滑的位置就只有 `15-13+1=3` 个样本。所以 **单 epoch 总样本约 540**，不到 Bridge 的 1/900。

**训练 budget 对比**

| 项 | Bridge（官方） | RoboTwin（目前配置） |
|---|---|---|
| `max_iter` | 150,000 | 150,000（继承 Bridge，未改） |
| `batch_size`（每 GPU） | 8 | 2 |
| GPU 数 | 假设 64 | 8 |
| 每 iter 样本数 | 8 × 64 = 512 | 2 × 8 = 16 |
| 总样本视次 | 150k × 512 = **76.8M** | 150k × 16 = **2.4M** |
| 等效 epoch 数 | 76.8M / 500k ≈ **150 epoch** | 2.4M / 540 ≈ **4,400 epoch** ⚠️ |

**这里有个巨大的 mismatch**：我们继承 Bridge 的 `max_iter=150k`，但数据少 900×，等效训练轮次多 30×——**过拟合是板上钉钉的**。

**为什么过拟合风险还不是灾难**

- 主干 DiT 大部分权重是 **Bridge 预训练先验**，不是白板从头训；它对"记住 180 个视频的具体细节"没有强烈倾向（参数空间远大于数据集）
- Action MLP 是真正从头训的，反而需要足够多的 iter 才能学会 14D 分布——这部分欠 iter 比过 iter 更危险
- Rectified flow loss 的目标是预测速度场，不是重建具体帧，泛化性比像素级 L1 loss 好

**实操建议（先观察再调）**

- **初期**（~5k iter）：action MLP 从随机权重往有意义的分布收敛，loss 降得快。这一阶段不要停。
- **中期**（5k~30k iter）：主要是 action MLP 和主干轻度联合 finetune。这里 **val loss** 开始变得有指示意义——如果 val loss 明显上升、train loss 还在降，说明过拟合，该停或加正则。
- **后期**（>30k iter）：只有数据集足够多样才适合训这么久；180 episode 的情况下，**经验上 20k~50k iter 已经接近饱和**，再训基本就是 memorize 训练集，不会对未见 episode 的生成质量有帮助。

**具体数字**（依赖后续实验验证，目前只是估算）：

| 阶段 | 建议 max_iter | 理由 |
|---|---|---|
| 第一次 smoke test | 2,000 | 验证 pipeline 跑通，每 500 存 ckpt |
| 先验验证 | 10,000 | action MLP 大致到位，能看到 action 条件生效 |
| 主要训练 | 20,000~30,000 | 180 episode 的合理上限，再多也是 memorize |
| 扩数据后 | 可按比例增加 | 比如加到 4 region（800 episode），max_iter 线性放到 80k |

**与 Bridge 对齐的另一种思路：按 epoch 数对齐**

Bridge 跑 ~150 epoch。我们想对齐 epoch 数：

- 150 epoch × 540 sample/epoch / 16 sample/iter = **~5,000 iter**

这个数字跟上面"smoke test / 先验验证"差不多，说明**如果只对齐 epoch 数，5k iter 就够了**——但这样 action MLP 可能没训充分（随机初始化需要更多梯度更新才能稳定）。

所以最终建议落在 **20k~30k iter**：既给 action MLP 足够的学习时间，又避免训练轮次过度超出 Bridge 的 epoch 节奏。

**扩数据路线图**

当前 200 episode（只用 pcp/pob 的 `region_all_clean`）是"跑通 pipeline 的最小集"。正式训练前应该扩到：

| 阶段 | 数据集组成 | Episode 数 | 备注 |
|---|---|---|---|
| 当前 | pcp + pob × `region_all_clean` | 200 | pipeline 验证 |
| 扩一倍 | 再加 `region_all_random_background`（增强泛化） | 400 | 抗背景干扰 |
| 扩四倍 | 加 `region_back` + `region_front`（全 region） | 800 | 视角多样性 |
| 扩十倍 | 再加新任务（不止 pcp/pob） | 2000+ | 任务多样性 |

这个顺序对应的是"每一步加的是什么信号"：background → viewpoint → task。扩到 800 episode 后，才比较有把握训 30k+ iter 不过拟合。

**三个脚本的公共部分**（都做的事）：

### 4.4 配置继承陷阱（详见 doc 6）

几个踩过的坑，细节在 [`6.RoboTwin后训练-配置继承陷阱与适配指南.md`](6.RoboTwin后训练-配置继承陷阱与适配指南.md)，这里只列名：

- **Hydra `defaults` 解析顺序**：父子配置同名字段，**子的赢**；但 `defaults` 列表里的 override 顺序会影响合并时机，不是想当然的"后者赢"。
- **`~dataloader_train.dataloaders`**：删除父配置 `dataloaders` 子树，否则 schema 冲突。上面 4.2 提到过。

- **`upload_reproducible_setup=False`**：父配置默认启用 S3 上传，本地环境必须关。
- **`straggler_detection`**：父配置开着，单机小 batch 跑会触发误报，`_8GPU` 实验里关掉（line 706-708）。

## 五、推理与可视化

### 5.1 RoboTwin 14D 推理

**脚本**：`scripts/inference_robotwin_val.sh`

```bash
bash scripts/inference_robotwin_val.sh              # 默认 iter 150000
bash scripts/inference_robotwin_val.sh 000074000    # 指定任意 iter
```

**关键字段**（脚本内部）：

- `CKPT`：`training_outputs/.../checkpoints/iter_${ITER}/model_ema_bf16.pt`（用 EMA BF16，体积 4 GB）
- `PARAMS`：`assets/action_conditioned/robotwin/inference_params.json`
- `EXP`：`cosmos_predict2p5_2B_action_conditioned_rectified_flow_robotwin_14d_13frame_256x320`
- `OUT`：`outputs/action_conditioned/robotwin_val_iter${ITER_SHORT}`（如 `..._iter74k`）

**推理参数对比 Bridge**（`inference_params.json`）：

| 字段 | 值 | 与 Bridge 的差异 |
|---|---|---|
| `input_root` | `/mnt/gyc_ckp/cosmos-predict2.5-robotwin` | Bridge 是 `assets/action_conditioned/basic/bridge` |
| `fps_downsample_ratio` | 10 | Bridge 是 1 |
| `action_load_fn` | `cosmos_predict2.action_conditioned.load_robotwin_action_fn` | Bridge 用 `load_default_action_fn` |
| `use_quat` | false | 同 Bridge（我们转欧拉角了，见 2.2） |
| `num_latent_conditional_frames` | 1 | 同 Bridge |
| `resolution` | `"256,320"` | 同 Bridge |
| `guidance` | 0 | 同 Bridge |

**`load_robotwin_action_fn` 的 14D 分支**（`cosmos_predict2/action_conditioned.py:289-342`）：

- 从 `state[:, 12:14]` 直读左右夹爪，**不读** `continuous_gripper_state`（见 doc 3 §3.1 的 gripper 非差分约定）
- 分别算左右臂的相对变换，拼成 `[T-1, 14]` 的 action
- scaler 是 `[20]×6 + [1] + [20]×6 + [1]`（左右臂各一份）

推理单卡跑（A800 80G），每个 episode 几分钟。`inference_params.json` 的 `start` / `end` 控制处理哪几个 val 文件（默认 5~8，即 3 个 episode）。

### 5.2 可视化与结果检查

每个 episode 推理后生成**两个文件**到 `OUT/`：

- `{episode_id}_chunk.mp4`：推理出来的生成视频，按 13 帧一 chunk 自回归拼接（见 doc 3 §5.2）
- `console.log` / `debug.log`：每个 chunk 的去噪 step / 耗时 / GPU 显存记录

**生成视频的结构**（以 `pob_0084_chunk.mp4` 为例，94 KB）：

- 第 1 chunk：**13 帧**（1 初始 + 12 生成）
- 之后每 chunk：**12 帧**（去掉重复的初始帧）
- 总帧数 ≈ 13 + 12 × (N-1)，其中 N 是 episode 的 action 序列长度 / 12

**快速浏览套路**：直接用 `mpv` 或 VS Code 的 mp4 preview 打开 `{episode_id}_chunk.mp4`，看整体画面是否连贯、机械臂是否按 action 移动、物体交互是否合理。

### 5.3 与 ground truth 对比

**脚本**：`scripts/eval_robotwin_compare.py`

**输入**：推理输出目录（含 `{ep_id}_chunk.mp4`）+ val annotation 目录 + 原始数据根目录

**输出**：对每个 episode 额外生成一个 `{ep_id}_compare_3.mp4`，**三联并排布局**：

```
┌─────────────┬─────────────┬─────────────┐
│ Ground Truth│  GT Downsample │  Generated  │
│ (原始 30fps) │ (降采样到 3fps) │  (我们的)   │
└─────────────┴─────────────┴─────────────┘
```

三列的作用：
- **左列 GT**：完整 30 fps 原始视频，参考动作的真实节奏
- **中列 GT Downsample**：按 `fps_downsample_ratio=10` 降采样后的版本，跟模型实际看到的时序一致，是**最公平的对比基准**
- **右列 Generated**：推理出来的视频

### 6.2 生成质量观察

基于 5 个 iter（4k / 10k / 20k / 74k / 104k）在 3 个 val episode（pob_0084 / 0088 / 0099）的推理结果：

**早期 (iter 4k)**：
- 画面虽然能动但**双臂动作和 GT 严重不符**
- 物体跟踪失败，机械臂经常跑偏
- 整体看像"知道要动，但不知道往哪动"

**中段 (iter 10k ~ 20k)**：
- 双臂运动方向开始对齐 GT
- 物体抓取/放置的轨迹基本可识别，但精度不够
- 偶尔有抖动 / 突变

**后期 (iter 74k ~ 104k)**：
- 双臂协调显著改善，运动节奏接近 GT
- 物体交互（抓取 / 放置）大致正确
- 仍有一些失败模式（见下）

**已知 failure mode**（基于 6 联对比视频肉眼观察）：
- 物体细节（尤其纹理 / 颜色变化）和 GT 仍有差距
- 长 chunk 自回归生成时，越往后画面越糊（误差累积）
- 双臂同时动作时，偶尔出现一只臂"卡住"

> 这些是定性观察，**没有量化指标**（PSNR / SSIM / FVD）。如果要对齐 Bridge 论文 Table 19 的评测口径，需要补一个 quantitative eval 流程。
